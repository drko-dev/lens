## 3. Brechas bloqueantes identificadas en código

### SEC-H8-01 — Modal sin comunicación funcional confirmada (CRÍTICA)

Archivo: packages/core/src/main/incident-storage/incident-confirmation-manager.ts.

La BrowserWindow se crea con nodeIntegration false, contextIsolation true y sandbox true **sin preload**. El HTML invoca window.electron.ipcRenderer.invoke para los botones, pero no se expone esa API desde el propio modal. **Los botones probablemente no efectúan ninguna transición**; requiere corrección y prueba con clic real en Electron.

### SEC-H8-02 — HTML no escapado en confirmación privilegiada (CRÍTICA)

generateModalHtml interpola directamente incidentTitle y justification dentro del documento HTML cargado como data:text/html, con scripts inline. Los textos provienen de contenido manipulable del incidente. Existe riesgo de inyección HTML/JavaScript **en la propia ventana autorizadora**. Preferir confirmación nativa desde Main (dialog.showMessageBox) sin HTML dinámico, o una ventana con recurso estático, textContent, CSP, preload y contextBridge mínimo, más pruebas adversariales.

### SEC-H8-03 — Identidad de emisor insuficiente (ALTA)

validateIpcSender rechaza eventos sin datos y subframes, pero acepta lens:// con cualquier host, file:// mediante subcadenas/sufijos genéricos y localhost:9191 sin cotejar el WebContents contra una ventana registrada, ni comprobar senderFrame === sender.mainFrame. Una URL aparentemente interna **no constituye identidad suficiente del invocador**.

### SEC-H8-04 — Respuesta de autorización no validada a nivel runtime (ALTA)

processConfirmationResponse trata REJECTED como rechazo y cualquier otro valor de decision como autorización, pese al tipo TypeScript. validateModalCaller comprueba solamente sender.id contra un conjunto, no la identidad completa del frame. Exigir decision exactamente APPROVED o REJECTED y vincular sender, frame, ventana y token.

### SEC-H8-05 — Ciclo de vida de tokens y promesas (MEDIA/ALTA)

El token se elimina antes de ejecutar la transición SQLite. Si la transición falla, el Promise de requestPrivilegedTransition queda pendiente por no invocar reject sobre el item. El TTL se evalúa al responder, sin cierre/rechazo activo por timeout. El valor confirmationToken se incluye en metadata persistida del timeline; evitar conservar tokens de autorización aun expirados y usar ID de auditoría no sensible. Verificar rechazo, caducidad, cancelación, concurrencia y fallo transaccional.

## 4. Aclaraciones de seguridad y alcance

- La confirmación interactiva local, aun corregida, **no prueba identidad de la persona mediante TouchID, Windows Hello, FIDO2 ni otro mecanismo del sistema operativo**. No denominar autenticación criptográfica a una confirmación visual.
- El Renderer principal conserva Node Integration por compatibilidad. H8.2 deberá imponer autorización en Main y no confiar en datos del Renderer.
- La retención comienza en modo manual/deshabilitado; la purga automática se programa al inicio solo bajo política habilitada. Preservar los invariantes transaccionales de casos fijados y cerrados.
- No tocar clústeres, ServiceAccounts, tokens reales, RC3/RC4 ni la rama develop durante el cierre documental.
- No hay base para afirmar que el build empaquetado de H8 funciona igual que Electron DEV hasta probarlo.
